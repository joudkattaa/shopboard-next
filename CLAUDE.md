# ROSEVEIL UI rules

- Preserve ROSEVEIL colors and typography. Prefer semantic utilities: bg-background, text-foreground, bg-primary, text-primary-foreground, border-border, text-muted-foreground. Raw palette utilities are for intentional brand decoration.
- Body: font-sans, DM Sans 400/500/600/700. Headings: font-heading, Cormorant Garamond 400/500/600. Do not substitute fonts or request unsupported weights.
- Keep all authored CSS in app/globals.css. Use Tailwind utilities in components; do not create component stylesheets.
- Reuse and compose the existing Base UI shadcn components without regenerating them. Retain accessible names, labels, keyboard behavior, and dialog semantics.
- Preserve visible keyboard focus: 2px semantic ring with 4px offset. Label inputs, communicate errors with text, respect reduced motion, and aim for 44px touch targets. Check contrast in both themes; decorative palette and chart aliases are not automatically suitable for body text.
- Use mobile-first responsive layouts with wrapping and no horizontal overflow. Original gutters: 16px, 24px at 480px, 40px at 900px, plus safe-area insets.
- Source radii are component-specific. Named xs/sm/md/lg/xl/2xl/3xl/4xl map to 2/3/5/8/10/16/20/32px. Exact uniform source values use rounded-roseveil-*; petal/editorial tokens preserve original asymmetric shapes. Preserve other source corner combinations when their components are migrated.
- Dark mode uses html[data-theme="dark"] and dark: utilities, never a .dark class. Server markup defaults explicitly to light. A future provider must synchronize saved/system preference safely; do not read browser storage during render or suppress hydration warnings.
- This phase provides foundations only. The starter page retains explicit demo colors; page styling and product features require their own approved phase.

## Reusable UI kit

- Reuse Button, Input, Card primitives, Badge, and Dialog exports from `@/components/ui/*`. Use `cn` from `@/lib/utils`; do not add another class-merging helper or duplicate primitives. Keep ProductCard as its existing feature-specific composition.
- Button variants: default (primary action), secondary, outline, ghost, destructive, link. Sizes: default (44px), lg (48px), xs/sm (compact), icon (44px), icon-xs/icon-sm (compact), icon-lg (48px). Compact buttons expand on coarse pointers; add an accessible name to every icon-only button. Use Base UI's `render` API and `nativeButton={false}` for links rather than nesting interactive elements.
- Badge variants: default, secondary, outline, ghost, destructive, link. A badge is a span by default, not a control. Use `render={<Link href="..." />}` for navigation; give interactive badges an adequate target area. Never convey status through color alone.
- Input preserves native props and Base UI `onValueChange`/Field integration. Always supply a visible label with matching htmlFor/id; associate help/error text with aria-describedby and set aria-invalid for errors. Placeholder text is not a label. Preserve disabled, required, autocomplete, and input-type semantics.
- Card/CardHeader/CardTitle/CardDescription/CardAction/CardContent/CardFooter are presentation primitives. CardTitle renders a div; supply a real heading inside it at the appropriate level. Do not make an entire Card a button around other controls.
- Compose DialogTrigger, DialogContent, DialogHeader, DialogTitle, DialogDescription, and DialogClose. Always provide a meaningful title and description. For intentionally absent descriptions, set aria-describedby={undefined} on DialogContent. Keep a visible close action, including when showCloseButton is false. Do not disable modal focus management or install competing Escape/focus-trap handlers. Use initialFocus/finalFocus only for a documented workflow; use onOpenChange event details to prevent dismissal only when necessary.
- Dialog keeps Base UI's default modal behavior, keyboard dismissal, focus trapping, and focus restoration. Its popup scrolls within the viewport; animations respect reduced motion. Verify focus behavior in a real browser for every new dialog workflow.
- Button, Input, Badge, and Dialog define Client Component boundaries for Base UI behavior. Card remains server-compatible. Keep route data loading in Server Components; put state and event handlers in the smallest consuming Client Component. Pass serializable props across server/client boundaries.
- Extend typed variants only for recurring UI needs. Prefer semantic tokens and className composition for local layout; all authored CSS remains in app/globals.css. Preserve visible focus and reduced motion. Do not replace working page compositions merely to demonstrate kit usage.
